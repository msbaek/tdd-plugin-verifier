# Claude Code와의 TDD 협업 — 두 검증 실험에서 얻은 기법들

이 문서는 [msbaek-tdd](https://github.com/msbaek/msbaek-claude-plugins/tree/main/msbaek-tdd) 플러그인을 **두 번의 독립 실험**으로 검증하며 얻은, 다른 프로젝트에도 옮겨 쓸 만한 기법을 정리한 것이다. 모든 사례에 실제 커밋·브랜치 근거가 있다 — 이론이 아니라 히스토리에서 재현 가능한 기록이다.

| | **실험 A** (이 저장소) | **실험 B** (선행 실험) |
|---|---|---|
| 시기 | 2026-08-15 ~ 16 | 2026-08-13 |
| 플러그인 | 1.38.0 | 1.18.0 ~ 1.26.0 |
| 도메인 | 결제 금액 계산 (쿠폰·마일리지·배송비) | 결제 금액 계산 **+ 체크아웃**(재고 차감) |
| 빌드·인수 채널 | Maven · 실제 HTTP → Spring → **MySQL(Testcontainers)** | Gradle · MockMvc + docker MySQL |
| 기어 브랜치 | `tdd-rgb-low`(39) / `mid`(7) / `high`(2) | `main`=low(42) / `rgb-gear-mid`(34) / `rgb-gear-high`(40) |
| 적대적 리뷰 | **세 기어 모두** (고위험 도메인이라 기어 무관 필수) | low·high만 (mid는 정의상 대상 아님) |
| 저장소 | 여기 | [msbaek-tdd-plugin-verification](https://github.com/msbaek/msbaek-tdd-plugin-verification) (보존용 archive) |

두 실험은 커밋 수가 아니라 **무엇을 검증했는지**가 다르다. B는 "기어마다 결함 검출력이 다른가"를, A는 "같은 코드에 리뷰를 세 번 돌리면 무엇이 더 나오는가"를 물었다. 아래 §1·§3에서 두 답이 만나 하나의 결론이 된다.

---

## 1. 방법론을 브랜치 실험으로 검증한다

"검토 밀도(기어)가 결과 품질에 정말 영향을 주는가?"를 논쟁 대신 실험으로 확인했다. 계획(요구사항·Gherkin·테스트 목록)이 확정된 커밋에서 브랜치 3개를 분기해, **기어만 바꿔** 같은 테스트 목록을 독립적으로 완주시킨다.

**실험 B의 결과 — 기어가 결함 잔존을 갈랐다.**

| 브랜치 | 기어 | 사람이 개입한 지점 | 결과 |
|---|---|---|---|
| `main` | low | R/G/B 각 단계마다 | 적대적 리뷰(별도 요청) 후 결함 0 |
| `rgb-gear-mid` | mid | 테스트 1개 사이클마다 | **CRITICAL 버그 잔존** (§3 오버셀) |
| `rgb-gear-high` | high | 완료 후 1회 (적대적 리뷰 필수) | 리뷰가 결함 발견 → 수정 후 결함 0 |

핵심은 커밋 수가 아니다. **사람의 단계별 검토(low)도, 사이클별 검토(mid)도 "여러 항목에 걸친 집계 불변식" 종류의 결함은 놓쳤다.** 그것을 잡은 것은 오직 적대적 리뷰였고, 두 브랜치가 독립적으로 같은 결함을 재발견했다(재현성). 리뷰 절차가 없는 mid 브랜치에는 그 버그가 의도적으로 남아 있다 — 그 차이 자체가 실험의 산출물이다.

**실험 A의 결과 — 커밋 단위는 히스토리의 밀도만 바꿨다.** A는 금액 계산이라는 고위험 도메인이라 기어와 무관하게 적대적 리뷰가 필수였고, 세 브랜치 모두 리뷰를 받았다. 그러자 최종 코드 품질은 세 기어가 같아졌고 달라진 것은 히스토리뿐이었다 — low는 R/G/B 리듬이 39커밋에 그대로 재생되고, high는 use case 하나가 커밋 하나로 압축된다.

> **두 실험을 합친 결론:** 기어는 *기록의 밀도*를 정하고, 결함 검출을 정하는 것은 *적대적 리뷰의 유무*다. 그러므로 기어를 올릴 때(high) 리뷰를 생략하는 것이 아니라, **기어와 무관하게 리뷰를 고정**하는 편이 안전하다.

이 패턴은 방법론 논쟁 일반에 적용할 수 있다. 프로세스 A와 B 중 무엇이 나은지 의견이 갈리면, AI 에이전트로 같은 작업을 두 프로세스로 완주시키고 diff를 비교하는 비용이 이제 충분히 싸다.

## 2. 서브에이전트로 TDD 규율을 구조적으로 강제한다

Red/Green/Blue를 각각 **별도 서브에이전트**에 위임하고, 각 프롬프트에 "할 일"만큼 "하지 말 것"을 명시한다.

- **Red**: 실패하는 테스트만. **프로덕션 코드 수정 금지** (컴파일 실패도 정당한 Red)
- **Green**: 지금 실패 중인 테스트를 통과시키는 **최소 구현만**. "이번 테스트가 요구하지 않는 로직(클램핑·이월·검증)은 만들지 마세요 — 다음 사이클의 몫"을 매번 명시
- **Blue**: 리팩터링만. "변경할 가치가 없으면 커밋 없이 사유만 보고"를 허용해 억지 리팩터링을 방지

효과는 히스토리에 남는다. 실험 A의 low 브랜치에서 계산기는 `return 0`(Fake It) → 필드 검증 → 상품 합계 → 쿠폰 clamp → 마일리지 이월 순으로 자랐고, 매 단계가 `test:`/`feat:`/`refactor:` 커밋으로 분리돼 어느 지점으로든 되돌릴 수 있다. 사람이 "미리 만들지 마"를 매번 감시하는 대신, **경계를 프롬프트에 새겨서 규율을 에이전트의 작업 범위 자체로 만든다.**

**커밋 권한도 규율의 일부다.** 플러그인 1.38.0의 high 기어는 R/G/B 에이전트가 `git add`까지만 하고 커밋을 보류하며, use case 전체가 끝난 뒤 오케스트레이터가 한 번에 커밋한다. 실험 A는 이 규칙이 실제로 지켜지는지를 검증 대상으로 삼았고(합격 기준: use case당 커밋 정확히 1개 + 작업 후 `git status` 클린), 두 조건 모두 충족했다.

**부수 발견 — "이미 green" 패턴.** 계획된 경계 테스트를 추가했는데 구현 변경 없이 통과하는 경우가 실험 B는 17사이클 중 5~6회, 실험 A는 21항목 중 7회 발생했다. 이것은 (a) 직전 Green이 과잉 구현했다는 신호일 수도 있고, (b) 최소 구현이 같은 동치류의 경계를 자연히 덮는 정당한 경우일 수도 있다. 어느 쪽인지 판단해 **커밋 메시지에 사유를 남기고 회귀 고정(regression pinning) 테스트로 그대로 커밋**하는 것이 실용적이었다(예: "E-9 구현의 전체 라인 순회가 이미 커버"). 특히 "우연한 산술 일치"는 메시지에 명시해 다음 테스트가 결함을 드러내게 한다.

## 3. 적대적 리뷰 — "전부 green"과 "맞다"는 다르다

전체 테스트가 green인 상태에서 적대적 리뷰("이 diff를 깨뜨려라, 평가하지 말고 공격하라")를 실행하면 실제 결함이 나온다. 두 실험에서 나온 결함을 유형별로 정리한다.

### 3-1. 집계 경계 — 검증 단위와 반영 단위가 다르면 그 차이가 곧 결함 (실험 B, CRITICAL)

```
장바구니: [("A", 수량2), ("A", 수량2)]   ← 같은 상품이 두 라인
재고: {"A": 3}
검증(라인별): 2≤3 ✓, 2≤3 ✓ → 통과
차감(누적):  3-2=1, 1-2=-1 → 재고 음수, 주문 성공(오버셀)
```

계획 단계에 "여러 라인 중 한 라인만 재고 부족"(서로 다른 상품) 테스트는 있었지만 "같은 상품이 여러 라인"은 없었다. 여기서 **검증 단위(라인)와 반영 단위(상품 합산)가 다르면 그 차이가 곧 결함**이라는 일반화가 나왔고, 플러그인의 경계 조건 식별 가이드에 다섯 번째 범주 **"집계 경계"** 로 반영됐다(1.20.0).

> **이 피드백 루프가 실제로 닫혔다.** 실험 A는 그 1.20.0 이후 버전으로 계획을 세웠고, §2 "경계 조건 5종 스캔 결과" 표의 집계 경계 행이 **계획 단계에서 자동으로** E-8("같은 상품이 두 라인으로 쪼개져도 결과는 같다")과 E-1(마일리지 한 자원이 상품·배송비 두 대상에 걸쳐 차감)을 요구했다. B가 사고로 발견한 결함 유형을 A는 설계로 덮었다 — 도구에 반영된 교훈은 다음 프로젝트에서 공짜가 된다.

### 3-2. 공허한(vacuous) 검증 — 지워도 안 깨지는 테스트 (두 실험 공통)

- **실험 B, MAJOR**: InMemory/JPA 동등성 계약 테스트가 항상 `save()`를 호출해서, `save()`를 no-op으로 바꿔도 통과했다(InMemory는 저장 인스턴스를 그대로 반환해 in-place 변경이 새고, JPA는 dirty checking이 자동 반영). "save() 없는 변경은 재조회 시 반영되지 않아야 한다"는 **negative 테스트**를 추가하자 JPA 어댑터가 managed entity를 그대로 반환하던 실제 결함까지 드러났다(`entityManager.detach()`로 수정).
- **실험 B, MAJOR**: `@ElementCollection(fetch = EAGER)` 결정을 LAZY로 되돌려도 아무 테스트도 깨지지 않았다(`@Transactional` 테스트는 세션이 열려 있어 LazyInit이 발생하지 않으므로). 트랜잭션 밖에서 컬렉션에 접근하는 테스트를 추가해 결정을 잠갔다.
- **실험 A, MAJOR**: 도메인 규칙 §1의 대표 예시(`lines=[(수량0), null]` → null 위반이 우선)가 테스트로 잠겨 있지 않아, **null 우선 로직을 지워도 기존 테스트가 하나도 안 깨졌다**. 예시 그대로의 고정 테스트를 추가(기존 구현으로 이미 green, 프로덕션 코드 변경 없음).

> 교훈: **설계 결정은 그 결정이 뒤집히면 실패하는 테스트가 있을 때만 보호된다.** "테스트가 있다"가 아니라 "그 결정을 지웠을 때 빨개지는가"로 확인한다.

### 3-3. 실패가 다른 실패로 위장 (실험 A, MAJOR ×2)

- **500이 400으로 위장**: 컨트롤러에 예외 핸들러가 없어 입력 유효성 위반이 500(서버 오류)으로 샜는데, 인수 테스트의 거부 단언이 "not 2xx"였던 탓에 이를 정상 거부로 오인했다. 단언을 4xx 검사로 강화해 버그를 Red로 재현한 뒤 `@ExceptionHandler`로 400 매핑을 추가.
- **그 수정이 만든 새 구멍**: 강화한 판정 `is4xxClientError()`가 이번엔 **404(장바구니 없음)까지 정상 거부로 삼켰다** — 조회 버그로 404가 나도 거부 시나리오가 전부 통과했을 것이다. `BAD_REQUEST` 정확 일치로 좁히고 404≠400을 증명하는 테스트를 추가.

> 교훈: **같은 코드에 리뷰를 여러 번 돌릴 가치가 있다.** 두 번째 결함은 첫 번째 리뷰의 *수정 결과*에 생긴 것이라, 한 번의 리뷰로는 원리적으로 잡을 수 없다. "not 2xx" 같은 느슨한 단언은 실패를 성공처럼 보이게 하는 것이 아니라, **다른 종류의 실패를 기대한 실패로 위장**시킨다.

### 3-4. 리뷰 지적도 검증 대상이다 (실험 A)

low 리뷰가 "필드 우선순위와 라인 순서가 충돌한다"고 지적했으나, §1 규칙을 재확인하니 구현이 이미 옳았다. 그래도 **리뷰어의 반례를 고정 테스트로 추가**해 우려를 영구히 해소했다. 리뷰 지적을 그대로 수용하면 옳은 코드를 망가뜨릴 수 있고, 그냥 기각하면 다음 리뷰가 같은 의심을 반복한다.

## 4. 에이전트의 자체 보고는 증거가 아니라 가설이다 (실험 A)

Walking Skeleton 단계에서 서브에이전트가 "BUILD SUCCESS"를 보고했다. 직접 재실행하니 **BUILD FAILURE**였다(가드 테스트가 404 수신). 이어서 반복 실행으로 성격을 규명했다 — 총 13회 중 12회 통과, 실패는 에이전트 작업 직후 첫 1회뿐이어서 컨테이너 콜드스타트 플레이키로 판정하고 진행했다.

- **규칙 1 — 항상 직접 재실행한다.** 자체 보고는 확인 대상이지 결론이 아니다.
- **규칙 2 — 한 번 통과했다고 끝이 아니다.** 컨테이너·네트워크가 끼면 통과율로 판단한다(1/1 통과와 12/13 통과는 다른 정보다).
- **규칙 3 — IDE 진단도 그 자체로는 증거가 아니다.** 같은 국면에서 IDE는 컴파일 에러 8건을 표시했지만 실제 `mvn compile`은 성공했다(편집 중간 스냅샷의 잔상). 보고와 진단이 엇갈리면 **빌드 도구를 심판으로 삼는다.**

## 5. 조용한 실패 카탈로그 — 테스트가 green인 채로 틀리는 경로

두 실험에서 실제로 밟은, "빌드는 성공하는데 의도와 다른" 함정 목록이다.

| 함정 | 증상 | 발견 경위 |
|---|---|---|
| **OSIV 부재 = off가 아니라 on** | 설정 항목이 없으면 기본값 `true` — "우리는 OSIV 안 쓴다"고 믿으며 켜 놓고 개발 | 실험 B: Walking Skeleton(MockMvc)은 세션이 열려 있어 우연히 통과, 계약 테스트가 그 밖으로 나가자 `LazyInitializationException` |
| dirty checking 자동 반영 | `save()` 없이도 변경이 저장된 것처럼 보임 | 실험 B, negative 계약 테스트 |
| `@Transactional` 상속 함정 | 추상 클래스에 선언된 `@Test`에는 서브클래스의 `@Transactional`이 적용 안 됨(declaring class 기준 탐색) | 실험 B, 세 브랜치 모두 독립적으로 조우 |
| Hibernate merge + 불변 리스트 | `List.of()`로 만든 엔티티 재저장 시 컬렉션 `clear()` 시도 → 예외 | 실험 B, mid 브랜치 계약 테스트 |
| p6spy 프로퍼티 키 오류 | 키가 틀려도 스타터 기본값으로 로그가 나옴 — **"로그가 나온다 ≠ 설정이 맞다"** | 실험 B, 크로스 세션 리뷰 |
| 컨테이너 콜드스타트 플레이키 | 첫 실행만 404, 이후 12회 연속 통과 | 실험 A, 자체 보고 검증 중 (§4) |
| 느슨한 단언이 실패를 위장 | "not 2xx"가 500을, `is4xxClientError()`가 404를 정상 거부로 흡수 | 실험 A, 적대적 리뷰 (§3-3) |

앞 5건이 JPA·인프라의 암묵 동작(영속성 컨텍스트·지연 로딩·자동 설정)에서 왔다. AI 에이전트는 명시적 코드는 잘 추론하지만 프레임워크의 암묵 동작은 사람과 똑같이(혹은 더 자주) 놓친다 — **에이전트와 협업할수록 암묵 동작이 적은 스택의 가치가 커진다.**

> **일반화 — "더하는 것"과 "기본값을 끄는 것"은 반대 규칙을 따른다.** 도구(approvaltests·p6spy)는 *최초로 필요해진 시점*에 추가해야 도입 커밋에 Why가 남는다. 반면 OSIV처럼 *이미 켜져 있는 기본값을 끄는 일*은 미룰수록 비싸진다 — 그 안전망 위에서 짠 코드가 끄는 순간 무효가 되기 때문이다(실험 B에서 실제로 3단계 낭비 발생: 우연한 통과 → 증상 우회(EAGER) → 되돌리기). 이 저장소의 [`application.yml`](../src/main/resources/application.yml)이 `open-in-view: false`를 사유 주석과 함께 명시하는 이유다.

## 6. 반복 오독되는 규칙은 산문이 아니라 예시로 고정한다 (실험 A)

도메인 규칙 §1의 검사 순서 문장("그 필드 값 검사에서 라인 순서를 따른다")을 **세 번의 독립 적대적 리뷰가 매번 반대로 읽었다** — low 리뷰는 필드 우선(field-major)으로, high 리뷰는 라인 우선(line-major)으로. 같은 문장이 세 번 다르게 읽혔다는 것은 독자의 문제가 아니라 문장의 문제다.

해결은 문장을 더 정교하게 다듬는 것이 아니라 **입력 → 기대 결과 예시 3개로 교체**하는 것이었다:

1. 같은 필드, 다른 라인 — `[(수량5), (수량0)]` → 두 번째 라인의 수량 위반
2. 다른 필드, 다른 라인 — `[(단가-1,수량5), (단가100,수량0)]` → 앞 라인의 단가가 아니라 **뒤 라인의 수량**(필드 우선순위가 라인 순서를 이김)
3. null 층 선행 — `[(수량0), null]` → 두 번째 라인의 null(null 검사가 전체 라인에 대해 필드 검사보다 먼저)

그리고 각 예시를 실행되는 테스트로 잠갔다. 규칙이 세 번 오독되는 동안 비용은 계속 커졌지만, 예시 3개를 넣은 뒤로는 오독이 멈췄다.

## 7. 세션 간 피드백 루프 — 도구를 쓰면서 도구를 고친다

두 저장소 모두 msbaek-tdd 플러그인의 검증 프로젝트다. 검증 세션과 플러그인 개발 세션이 **서로 메시지를 주고받으며** 실사용에서 발견한 문제를 곧바로 플러그인에 반영했다.

- 실험 B가 p6spy 설정을 플러그인 세션에 전달 → 플러그인 세션이 공식 문서와 대조해 **이쪽 설정의 프로퍼티 키 오류를 역으로 발견** → 검증 저장소 수정 + 플러그인에는 함정 경고로 반영(1.18.0)
- 실험 B의 오버셀 결함 → 경계 조건 "집계 경계" 범주로 승격(1.20.0) → **실험 A가 그 항목의 수혜자**(§3-1)
- 실험 B의 도구 도입 시점 논의 → OSIV 항상 off·approvaltests/p6spy는 트리거 시점 도입으로 정리(1.26.0)
- 실험 A는 플러그인 세션의 요청으로 시작됐다 — "1.38.0에서 high 기어 커밋 단위가 바뀌었으니 세 기어를 각각 별도 브랜치로 검증해 달라"는 크로스 세션 요청이 이 저장소의 3브랜치 구조를 만들었다

포인트는 **전달 형식**이다. "이런 게 좋겠다"가 아니라 **재현 시나리오 + 근거 커밋 해시 + 어느 브랜치에서 발생했는지**를 붙여 보내면, 받는 쪽이 검증하고 반영 여부를 판단할 수 있다.

## 8. 작은 기법들

- **Scenario Outline의 Examples 블록 분리** — 여러 행짜리 Examples 표를 행 단위 RGB 사이클로 나누려면 블록을 쪼개 각각 `@pending`을 붙인다(Outline 레벨 태그는 전체 상속이라 행별 제어가 안 된다). 각 Green 커밋이 자기 행의 태그만 해제한다.
- **문서-실행 드리프트 차단** — 계획 문서의 Gherkin(§2)은 파생 뷰이고 실행되는 정본은 `.feature`라고 문서에 선언한다. 기대값이 코드와 어긋나면 빌드가 깨지므로 문서가 조용히 낡을 수 없다.
- **표현 불가능한 시나리오는 정직하게 제외한다** — 실험 A의 E-14/E-15(라인 목록 null)는 cartId 기반 REST 채널로는 입력 구성 자체가 불가능했다. 시나리오를 지우지 않고 `@api-enforced` 태그로 남기되, 주석에 "만족됨(satisfied)"이 아니라 **"구성 불가(inexpressible)"** 라고 적고 순수 함수 계약은 단위 테스트로 이관했다.
- **범위 지어내기 거절도 기록한다** — 실험 A의 §7(JPA Repository 계약 테스트)은 비교할 두 번째 구현(InMemory)이 애초에 없어서 수행하지 않았다. 단계를 조용히 건너뛰는 대신 **"왜 하지 않았는가"를 문서에 남긴다**(실험 B는 InMemory/JPA 두 구현이 있었으므로 계약 테스트가 유효했다 — 같은 단계라도 프로젝트 조건에 따라 답이 갈린다).
- **의존성 없이 property 테스트하기** — jqwik 도입 대신 고정 시드 `Random`으로 500회 샘플링해 불변식(최종 금액 ≥ 0)을 검증했다. 시드가 고정이라 재현 가능하다.
- **한글 커밋 메시지 안전 처리** — heredoc은 인코딩이 깨질 수 있어 임시 파일 + `git commit -F`로 통일한다.
- **phase별 커밋 = 되돌리기 단위** — `test:`/`feat:`/`refactor:` 분리 덕에 자율 진행(high) 중에도 어떤 테스트 단위로든 revert가 가능한 상태가 유지된다.
- **백그라운드 보안 리뷰의 이중 방어** — 실험 B의 high 브랜치에서 오버셀 버그가 커밋되자 커밋 훅의 보안 리뷰가 적대적 리뷰와 **독립적으로** 같은 결함을 플래그했다. 서로 다른 각도의 자동 검토가 겹치면 한쪽이 놓쳐도 잡힌다.
