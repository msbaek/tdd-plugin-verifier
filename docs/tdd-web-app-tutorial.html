Web App을 TDD로 구현하는 7단계

장바구니 결제 금액 계산을 예제로, 요구사항 문서부터 REST + JPA + MySQL 관통 인수 테스트와 적대적 리뷰까지. 각 단계는 명령 → 생기는 것 → 확인 순서다.

준비물 Claude Code + msbaek-tdd plugin Java 21 · Maven Docker 실행 중 (Testcontainers)

정본은 하나

모든 숫자·규칙의 정본은 Cart.md §1. Gherkin·테스트·코드는 그 파생 뷰다.

승인 후 커밋

에이전트는 초안만 쓴다. 단계마다 내가 결정하고, 커밋한 뒤 다음으로.

직접 검증

에이전트의 "BUILD SUCCESS"는 믿지 말고 mvn test를 직접 돌린다.

1

요구사항 문서 쓰기

플러그인 실행 전, 도메인 규칙을 마크다운 한 장으로 직접 적는다.

# docs/calculate-cart-requirements.md
- 장바구니 금액 산출. 부수효과 없는 순수 계산.
- TDD 유형: web-app, rest, jpa, mysql

## 도메인 규칙 (0층)
- 상품 합계 = Σ(단가 × 수량). 배송비 고정 3,000원(빈 장바구니는 0원).
- 적용 순서(불변식): 상품 합계 → 쿠폰 → 마일리지 → 배송비 합산
- 쿠폰: 상품 합계에서만 차감, 초과분 소멸.
- 마일리지: 상품 잔액 → 배송비 순으로 차감, 상한 초과분은 미사용.
- 최종 결제 금액 = 상품 잔액 + 배송비 잔액. 항상 ≥ 0.

완벽할 필요 없다 — 모호한 부분은 다음 단계에서 에이전트가 질문으로 끌어낸다. 단 핵심 불변식(적용 순서)만은 반드시 명시한다.

2

프로젝트 생성

Maven 프로젝트와 8단계 템플릿 문서가 생긴다.

/tdd web-app com.example.cart.Cart
  • pom.xml — Spring Boot + JPA + Cucumber + Testcontainers
  • src/test/.../Cart.md — 8단계 체크리스트 템플릿. 이후 모든 진행 기록·정본이 이 파일에 쌓인다
생성 확인 후 첫 커밋. 이후 매 단계 승인마다 커밋한다.
3

계획 수립

도메인 규칙 → Gherkin → Unit Test 목록을 에이전트가 초안하고, 내가 승인한다.

/tdd-plan @docs/calculate-cart-requirements.md
  • §1 도메인 규칙 — 대표 입력 1건의 검산 전개 표(숫자의 정본)가 만들어진다
  • §2 Gherkin — 규칙·검산 표를 시나리오로 변환 (이 예제: 15개)
  • §4 Unit Test 목록 — Gherkin이 못 다루는 세밀 분기만. 전체를 Degenerate→General 순으로 정렬한 구현 순서표가 나온다

에이전트가 모호한 것(null 정책, 검증 책임, 범위)을 질문하면 답만 하면 된다 — 지어내지 않는 것이 설계다.

§1~§4 승인이 끝나면 plan-critic이 문서를 적대적으로 검증한다(모순·정본 이중화·경계 누락). 이 예제는 2회 반려 후 3차에 통과했다.

plan-critic PASS까지 반복. 통과 전에는 코드를 쓰지 않는다.
4

인수 테스트 셋업

§2 Gherkin이 실행 가능한 .feature가 된다. 전부 @pending이라 빌드는 그린.

/cucumber-acceptance
  • cart-checkout.feature + Runner → Steps → Protocol Driver → SUT (Four Layer)
  • Runner 필터 "not @pending" — RGB에서 Green마다 자기 시나리오의 태그를 해제한다
mvn test → BUILD SUCCESS, 시나리오 전부 skipped(의도됨), undefined step 없음.
Driver가 원하는 채널인지 직접 열어 확인하라. 기본값은 빠른 in-process 호출이다. 이 예제는 사용자 결정으로 실제 HTTP → Spring 앱 → MySQL 관통으로 교체했고(API는 cartId로 DB에서 라인 조회), 그 결정을 Cart.md에 기록했다.
5

Walking Skeleton

가장 얇은 슬라이스로 HTTP → 앱 → MySQL을 먼저 관통시킨다. 계산 로직은 아직 스텁.

  • JPA 엔티티 + Repository + POST /carts/{cartId}/checkout + Testcontainers 연결
  • 관통이 목적이지 완성이 목적이 아니다
에이전트 보고와 무관하게 mvn test를 직접 돌린다. 이 예제에선 에이전트의 "BUILD SUCCESS"가 거짓이었고, 반복 실행(13회 중 12회 통과)으로 콜드스타트 플레이키임을 확인한 뒤 진행했다.
6

RGB 사이클로 구현

§4의 순서표를 따라 한 항목씩. 기어를 먼저 고른다 — 기어는 커밋 단위다.

/tdd-rgb
기어커밋 단위이 예제 결과
lowR / G / B 각 phase마다39 커밋 — 학습·감사용
mid테스트 사이클(R+G+B)마다7 커밋 — 일상 개발의 균형점
highuse case 하나 = 커밋 하나2 커밋 — 에이전트는 add까지만

사이클의 리듬 (가장 퇴화한 케이스부터):

  • Red — Gherkin이면 @pending 해제, unit이면 테스트 추가. 실패를 눈으로 확인
  • Green — 통과할 최소 구현 (첫 케이스는 return 0도 정답)
  • Blue — 반복이 눈에 띄면 정리 (예: 검증 4개 쌓인 뒤 validate() 추출)
"이미 green"은 정상이다. 앞선 일반화가 뒤 케이스를 덮으면, 테스트만 추가하는 커밋으로 행동을 고정하고 체크리스트에 사유를 남긴다. 채널로 표현 불가능한 시나리오는 태그(@api-enforced)로 제외하고 단위 테스트로 이관한다.
체크리스트 전 항목 완료 + 전체 mvn test 그린 + git status 클린.
7

적대적 리뷰로 마무리

금액 계산 같은 고위험 도메인은 완료 시 적대적 리뷰가 필수다. 시작 커밋..HEAD diff를 리뷰어에게 준다.

이 예제에서 세 번의 독립 리뷰가 매번 서로 다른 진짜 결함을 찾았다:

  • 입력 위반이 500으로 새는데 인수 테스트가 정상 거부로 오인 → 400 매핑 추가
  • 수정한 4xx 판정이 이번엔 404까지 삼킴 → 400 정확 일치로 정밀화
  • 규칙 문장을 리뷰마다 반대로 읽음 → 문장 대신 구체 예시 3개로 재작성

MAJOR 지적은 항상 Red로 재현 → 수정 → Green 순서로 처리한다. 리뷰 지적 자체도 검증 대상이다 — 확인해 보니 구현이 이미 옳았다면, 리뷰어의 반례를 고정 테스트로 추가해 우려를 영구히 해소한다.

MAJOR 0건 + 전체 그린이면 끝.
