## 1. 요구사항 — 도메인 규칙(0층) + User Story

> 원천: `docs/calculate-cart-requirements.md`
> **숫자의 정본은 아래 "검산 전개" 하나다.** 단계 2 Gherkin의 `Examples` 표를 비롯한
> 이후 모든 수치는 이 전개에서 옮겨온 **파생 뷰**이며, 각자 다시 계산하지 않는다.

### 도메인 규칙 (0층)

- 기본 규칙
    - 장바구니는 0개 이상의 라인을 가진다. 라인 = (상품, 단가, 수량), 수량 ≥ 1.
    - **상품 합계** = 모든 라인의 (단가 × 수량) 합.
    - **배송비**는 주문당 고정 3,000원. 단, 빈 장바구니(라인 0개)는 배송비도 0원.
    - **쿠폰은 주문당 최대 1개(단일 금액)로 적용한다.** 여러 장을 합산하거나 라인별로
      나눠 적용하는 규칙은 없다 — 입력의 쿠폰은 항상 금액 하나다.
    - 모든 금액은 원 단위 정수이며 음수가 될 수 없다.
- 특별 규칙 — 할인 적용 순서가 불변식
    - 적용 순서: **상품 합계 → 쿠폰 할인 → 마일리지 차감 → 배송비 합산**.
      이 순서는 불변식이며 바꾸면 결과가 달라진다(쿠폰이 배송비를 깎지 못한다는 점이 순서로 표현된다).
    - **쿠폰 할인(1단계)** — 상품 합계에서만 차감한다.
        - 쿠폰 금액이 상품 합계를 초과하면 상품 잔액은 0원에서 멈춘다. **초과분은 소멸**한다(이월·환급 없음).
        - 예: 상품 합계 3,000원에 5,000원 쿠폰 → 상품 잔액 0원, 쿠폰 초과분 2,000원 소멸(고객 손해 효과).
    - **마일리지 차감(2단계)** — 쿠폰 적용 **후 잔액** 기준으로 차감한다.
        - ① 먼저 상품 잔액에서 차감한다.
        - ② 상품 잔액이 0원에 도달하면, 남은 마일리지는 **배송비에서 추가 차감**한다.
        - ③ 배송비도 0원에 도달하면, 그 이상의 마일리지는 **사용되지 않는다**
          (소멸이 아니라 **미사용** — 차감 상한. 쿠폰 초과분의 소멸과 구별된다).
        - 따라서 마일리지 사용액의 상한 = (쿠폰 적용 후 상품 잔액) + 배송비.
    - **최종 결제 금액** = 상품 잔액 + 배송비 잔액. 항상 ≥ 0.
    - **빈 장바구니에 쿠폰·마일리지가 양수로 주어져도** 위 순서를 그대로 적용한다 —
      상품 합계가 0이므로 쿠폰은 0에서 멈추고(초과분 소멸), 배송비도 0이므로 마일리지는
      차감할 대상이 없어 **전액 미사용**이다. 최종 결제 금액은 0원이며, 별도의 거부 규칙을
      두지 않는다(잘못된 입력이 아니라 정상 입력의 경계다).
    - 미사용 마일리지(상한 초과분)는 계산 결과에 노출하지 않는다 — 최종 결제 금액만 반환한다(사용자 결정).
- 입력 유효성 — 계산기가 검증 책임을 가진다(사용자 결정)
    - **null 입력도 명백히 잘못된 입력이다**(사용자 결정) — 수량 < 1·단가 < 0과 동일하게
      거부(예외)한다. 대상은 세 가지다.
        - ① **계산 요청 자체가 null**
        - ② **라인 목록이 null** — "0개 이상의 라인"은 **빈 리스트**를 뜻하며 null이 아니다.
          빈 리스트는 정상 입력(빈 장바구니, 최종 0원)이고 null은 거부다.
        - ③ **라인 목록 안의 개별 라인 자체가 null** — 라인 값 객체는 단가·수량을 원시
          타입(예: `long`/`int`)으로 가지므로 필드 자체는 null이 될 수 없다. 이 항목은
          **라인 참조가 null인 경우만** 가리키며, 값이 유효 범위를 벗어나는 것(단가<0
          등)은 아래 필드 유효성 검사가 별도로 다룬다.
    - 수량 < 1, 단가 < 0, 쿠폰 < 0, 마일리지 < 0 등 명백히 잘못된 입력은 계산기가 거부한다(예외).
    - **검사 순서(정본)** — 여러 입력이 동시에 잘못된 경우, 아래 순서로 검사해 **가장 먼저
      걸리는 위반 하나만** 예외로 던진다. 전체 위반 목록을 모아 반환하지 않는다(구현 단순화 우선).

          요청 자체 null → 라인 목록 null → 개별 라인 null → 수량 < 1 → 단가 < 0 → 쿠폰 < 0 → 마일리지 < 0

      즉 **null 검사가 필드 유효성 검사보다 항상 먼저**이고(참조가 없으면 필드를 볼 수 없다),
      필드 유효성 안에서는 **수량 → 단가 → 쿠폰 → 마일리지** 순이다.

      **라인 순서 규칙의 적용 범위**: "라인이 여러 개면 앞 라인의 위반이 우선"은 **필드
      유효성 검사 단계 내부에서만** 적용된다 — 즉 모든 라인이 null이 아님을 먼저 확인(개별
      라인 null 검사가 전체 라인 목록에 대해 먼저 끝난 뒤)한 다음에야 필드 값 검사로
      넘어가며, 그 필드 값 검사에서 라인 순서를 따른다. 따라서 `lines=[(수량0), null]`처럼
      null 라인과 필드 위반이 섞이면: ① 모든 라인의 null 여부를 먼저 훑어 두 번째 라인의
      null을 예외로 던진다(null 층이 전체 라인에 대해 필드 층보다 항상 먼저) — 첫 라인의
      "수량<1"은 검사되지 않는다. 이 순서가 정본이며, 단계 2 Gherkin과 단계 4 unit
      test(U-1, U-4, U-8, U-9)는 이 문장의 파생 뷰다.
    - 마일리지가 고객의 보유 잔고를 초과하는지, 쿠폰이 유효한지 등 **외부 상태 의존적 검증**(잔고 조회, 쿠폰 유효기간 등)은 이 스토리 범위 밖 — 상위 계층(장바구니 조회/주문 흐름)의 책임이다.

#### 검산 전개 (숫자의 정본) — 대표 입력 1건

마일리지가 상품 잔액과 배송비 **양쪽에 걸쳐** 차감되는 케이스를 대표 입력으로 삼는다
(적용 순서 불변식의 모든 단계가 한 번에 드러난다).

입력
- 라인 1: 단가 12,000원 × 수량 2
- 라인 2: 단가 5,000원 × 수량 1
- 쿠폰 5,000원, 마일리지 26,000원

|---|---|---|---|---|
| 0. 상품 합계 | 12,000×2 = 24,000, 5,000×1 = 5,000 → 24,000+5,000 | 29,000 | (미합산) | |
| 1. 쿠폰 할인 | 29,000 − 5,000 | 24,000 | (미합산) | 쿠폰 전액 사용, 소멸분 0 |

### User Story (기능 나열)

#### US-1 — 장바구니 결제 금액 계산 (주 스토리)

    As a    장바구니에 상품을 담고 쿠폰·마일리지를 보유한 고객
    I want  쿠폰과 마일리지가 정해진 순서대로 적용된 최종 결제 금액을 계산해 주기를
    So that 결제하기 전에 내가 실제로 낼 금액을 알고 구매를 결정할 수 있다

- **Valuable**: 결제 전에 실제 부담액을 알 수 있다 — 쿠폰 초과분 소멸처럼 손해가 나는
  조합도 결제 전에 드러난다(사용자 언어).
- **Small**: **계산 규칙**이 부수효과 없는 순수 함수 한 단위다(입력 → 최종 결제 금액).
  쿠폰 발급·마일리지 적립/차감 저장·주문 생성은 이 스토리에 포함하지 않는다.
  이 계산을 HTTP로 노출하고 장바구니 라인을 DB에서 가져오는 **배달 메커니즘**은 같은
  스토리를 동작시키는 별도 관심사이며, 아래 "범위(Scope)"에서 구분한다.
- **Testable**: 위 검산 전개의 수치가 그대로 기대값이 되므로 단계 2 Gherkin
  `Scenario Outline` + `Examples`로 검증 가능하다(입력 → 최종 결제 금액).

> US-2(금액 구성 내역 확인)는 사용자 확인 결과 삭제됨 — 최종 결제 금액만 반환하고 구성
> 내역(상품 잔액·배송비 잔액·마일리지 사용액)은 노출하지 않는다.

### 범위(Scope) — 사용자 확인 결과

- 이번 tdd-plan은 **원천 문서대로 REST + JPA + MySQL까지 포함**한다(web-app 8단계 템플릿 그대로 진행).
- **US-1의 "Small"과 이 Scope는 서로 다른 층을 말하므로 모순이 아니다.** US-1이 정의하는
  단위는 **계산 규칙(도메인 규칙 0층)** 자체이고, 이는 부수효과 없는 순수 함수다 —
  같은 입력이면 언제나 같은 최종 결제 금액이 나오고 DB·HTTP를 알지 못한다. 반면
  REST + JPA + MySQL은 그 계산 규칙을 **바깥에 노출하고 구동하는 배달 메커니즘**이다:
  HTTP 요청을 계산 입력으로 바꾸는 일은 §5 Walking Skeleton, 장바구니 라인을 DB에서
  가져오는 일은 §7 JPA Repository가 각각 맡는다. 계산 규칙을 키우지 않은 채 그 둘을
  덧붙이는 것이므로 US-1은 여전히 한 단위로 남는다.
    - 따라서 §5·§7이 커져도 §1의 도메인 규칙과 검산 전개는 바뀌지 않는다 — 이 절의
      수치가 정본이고, REST 응답·DB 조회 결과는 그 파생이다.
- 입력 유효성은 계산기 책임(위 도메인 규칙의 "입력 유효성" 항목 참조), 외부 상태 의존적
  검증(잔고·쿠폰 유효기간)은 범위 밖.

### 인수 테스트 채널 결정 (사용자 재확인 — §3 셋업 이후 변경)

- 인수 테스트(§3 `.feature`)는 **in-process 계산 호출이 아니라 실제 HTTP → 실제 Spring
  앱 → 실제 MySQL(Testcontainers)까지 관통**해야 한다(사용자 결정). `cucumber-acceptance`
  스킬의 기본 권장(in-process driver 우선, 속도)보다 이 프로젝트에서는 REST+JPA+MySQL
  파이프라인 검증이 우선한다.
- REST API는 **장바구니 ID로 DB에 저장된 라인을 조회**한다(요청 본문에 라인을 직접
  담지 않음). 즉 POST 요청은 `cartId · coupon · mileage`만 받고, 라인은 Repository가
  MySQL에서 가져온다. Given 스텝은 그 라인을 미리 DB에 시드한다.
- **파급**: §1의 계산 규칙(도메인 규칙 0층, `CartCalculator.calculate(CalculateCartRequest)`)은
  그대로 순수 함수로 남는다 — 바뀌는 것은 그 앞단이다. Walking Skeleton(§5)의 Controller가
  `cartId`로 JPA Repository에서 라인을 조회해 `CalculateCartRequest`를 만들고 계산기에
  위임하는 역할을 맡는다. 이 결정으로 §5(Walking Skeleton)와 §7(JPA Repository)의
  핵심 골격이 §3 인수 테스트 인프라와 함께 앞당겨 구축된다 — §3의 Driver가 in-process
  호출 대신 `TestRestTemplate`(또는 `MockMvc`) + 실제 MySQL 시드로 교체된다.

## 2. Gherkin Scenario

> **숫자의 정본은 §1 "검산 전개"다.** 아래 `Examples` 표의 모든 수치는 그 전개(대표 입력 1건 +
> 부속 검산 표)에서 **옮겨온 파생 뷰**이며 여기서 다시 계산하지 않는다.
> `/cucumber-acceptance` 적용 시 실행되는 원본은 이 Gherkin을 그대로 옮긴 `.feature` 파일이다.
>
> 출력은 **최종 결제 금액 하나**뿐이다(§1: 구성 내역·마일리지 사용/미사용액은 노출하지 않음).
> 따라서 모든 `Then`은 최종 금액 또는 거부 여부만 검증한다.

```gherkin

  Rule: 적용 순서(상품 합계 → 쿠폰 → 마일리지 → 배송비 합산)가 최종 금액을 결정한다   # ← US-1

    # §1 검산 전개의 대표 입력. 마일리지가 상품 잔액과 배송비 양쪽에 걸치는 케이스로,
    # 적용 순서 불변식의 네 단계가 한 시나리오에 모두 드러난다(happy path).
    Scenario: E-1. 쿠폰과 마일리지가 순서대로 적용된 최종 결제 금액
      Given 장바구니에 단가 12000원 상품이 2개 담겨 있다
      And 장바구니에 단가 5000원 상품이 1개 담겨 있다
      And 쿠폰 5000원을 사용한다
      And 마일리지 26000원을 사용한다
      When 결제 금액 계산을 요청하면
      Then 최종 결제 금액은 1000원이다

    # §1 "부속 검산" 표. 상품 합계 29000 · 쿠폰 5000(→ 상품 잔액 24000) 고정, 마일리지만 변경.
    # 마일리지 사용 상한 = 24000 + 배송비 3000 = 27000 (E-4가 그 경계, E-5가 경계 초과).
    # 케이스 라벨에 E-3이 없는 이유: 마일리지 26000(상품 잔액 소진 후 배송비에서 추가 차감)
    # 행은 E-1과 입력·기대값이 문자 그대로 동일해 제거했다. 그 케이스는 E-1이 전담한다.
    Scenario Outline: <케이스>. 마일리지 차감 범위에 따른 최종 결제 금액
      Given 장바구니에 단가 12000원 상품이 2개 담겨 있다
      And 장바구니에 단가 5000원 상품이 1개 담겨 있다
      And 쿠폰 5000원을 사용한다
      And 마일리지 <마일리지>원을 사용한다
      When 결제 금액 계산을 요청하면
      Then 최종 결제 금액은 <최종금액>원이다

      Examples:
        | 케이스 | 마일리지 | 최종금액 | 걸리는 규칙                                  |
        | E-2   | 10000  | 17000  | 상품 잔액 내에서만 차감(배송비 3000 그대로)       |
        | E-4   | 27000  | 0      | 경계: 상한(24000+3000)을 정확히 소진            |
        | E-5   | 30000  | 0      | 경계 초과: 3000은 미사용(결과에 노출되지 않음)     |

  Rule: 쿠폰은 상품 합계에서만 차감되고, 초과분은 소멸한다   # ← US-1

    # §1 부속 검산(쿠폰 초과 경계). 쿠폰 전액이 상품 합계 안에서 소진되는 정상 케이스는
    # E-1이 이미 덮는다. 여기는 "쿠폰이 배송비를 깎지 못한다"가 드러나는 초과 케이스만.
    Scenario: E-6. 쿠폰이 상품 합계를 초과해도 배송비는 깎이지 않는다
      Given 장바구니에 단가 3000원 상품이 1개 담겨 있다
      And 쿠폰 5000원을 사용한다
      And 마일리지 0원을 사용한다
      When 결제 금액 계산을 요청하면
      Then 최종 결제 금액은 3000원이다

  Rule: 배송비는 주문당 고정 3000원이며, 빈 장바구니는 0원이다   # ← US-1

    # 3000원 고정은 E-1~E-6이 이미 덮는다. 여기는 크기 경계(라인 0개)만.
    Scenario: E-7. 빈 장바구니는 배송비도 붙지 않는다
      Given 장바구니가 비어 있다
      And 쿠폰 0원을 사용한다
      And 마일리지 0원을 사용한다
      When 결제 금액 계산을 요청하면
      Then 최종 결제 금액은 0원이다

    # §1 부속 검산 표 마지막 행(라인 0개 · 쿠폰 5000 · 마일리지 10000 → 최종 0원).
    # §1: "빈 장바구니에 쿠폰·마일리지가 양수로 주어져도 위 순서를 그대로 적용한다 …
    # 별도의 거부 규칙을 두지 않는다(잘못된 입력이 아니라 정상 입력의 경계다)."
    # 즉 쿠폰 5000은 상품 합계 0에서 멈춰 전액 소멸하고, 배송비도 0이라 마일리지 10000은
    # 전액 미사용이다. E-7과 달리 "거부"가 아니라 0원 계산 성공임을 고정한다.
    Scenario: E-13. 빈 장바구니에 쿠폰·마일리지가 있어도 거부되지 않고 0원이다
      Given 장바구니가 비어 있다
      And 쿠폰 5000원을 사용한다
      And 마일리지 10000원을 사용한다
      When 결제 금액 계산을 요청하면
      Then 최종 결제 금액은 0원이다

  Rule: 같은 상품이 여러 라인으로 나뉘어도 상품 합계는 누적으로 계산된다   # ← US-1 (집계 경계)

    # E-1과 상품 구성이 동일하되 12000원 상품만 2개 라인으로 쪼갠 입력.
    # 계산이 라인 단위로만 이뤄지고 누적되지 않으면 여기서 깨진다. 기대값은 E-1과 같아야 한다.
    Scenario: E-8. 같은 상품이 두 라인으로 쪼개져도 결과는 같다
      Given 장바구니에 단가 12000원 상품이 1개 담겨 있다
      And 장바구니에 같은 단가 12000원 상품이 1개 더 담겨 있다
      And 장바구니에 단가 5000원 상품이 1개 담겨 있다
      And 쿠폰 5000원을 사용한다
      And 마일리지 26000원을 사용한다
      When 결제 금액 계산을 요청하면
      Then 최종 결제 금액은 1000원이다

  Rule: 명백히 잘못된 입력은 계산기가 거부한다   # ← US-1 (입력 유효성)

    # §1 검사 순서(정본): 요청 자체 null → 라인 목록 null → 개별 라인 null → 수량 < 1
    # → 단가 < 0 → 쿠폰 < 0 → 마일리지 < 0. 아래 시나리오 배치도 이 순서를 따른다
    # (E-14·E-15 = null 층, E-9~E-12 = 필드 유효성 층, E-16 = 라인 순서 규칙).
    # 예외 타입·메시지는 여기서 고정하지 않고 단계 4 unit test로 위임한다.
    # 외부 상태 의존 검증(마일리지 잔고·쿠폰 유효기간)은 §1대로 범위 밖 — 여기 없음.

    # null은 Examples 표의 "값" 칸에 넣으면 문자열 "null"과 구분되지 않아 별도 Scenario로 둔다.
    # §1: "'0개 이상의 라인'은 빈 리스트를 뜻하며 null이 아니다" — E-7(빈 리스트 = 정상 0원)과
    # 정확히 반대 결과가 나와야 하는 짝 시나리오다.
    Scenario: E-14. 라인 목록 자체가 null이면 거부된다
      Given 장바구니 라인 목록이 null인 계산 요청이 준비되어 있다
      When 결제 금액 계산을 요청하면
      Then 계산이 거부된다

    # §1 null 3종 중 ③. 라인 목록은 있으나 그 안의 원소가 null인 경우 —
    # 목록 참조만 확인하고 원소를 확인하지 않는 얕은 구현을 잡는다.
    Scenario: E-15. 라인 목록 안에 null 라인이 섞여 있으면 거부된다
      Given 장바구니에 단가 12000원 상품이 2개 담겨 있다
      And 장바구니에 null인 라인이 하나 더 담겨 있다
      And 쿠폰 0원을 사용한다
      And 마일리지 0원을 사용한다
      When 결제 금액 계산을 요청하면
      Then 계산이 거부된다

    # 각 필드가 단독으로 위반하는 최소 케이스. 라인은 1개이므로 "어느 라인"의 모호함이 없다
    # (다중 라인에서의 라인 순서 규칙은 E-16이 담당).
    Scenario Outline: <케이스>. 잘못된 입력 거부
      Given 장바구니에 단가 10000원 상품이 1개 담긴 계산 요청이 준비되어 있다
      And 쿠폰 0원, 마일리지 0원이 주어져 있다
      And 그 요청의 <필드>가 <값>으로 덮어써진다
      When 결제 금액 계산을 요청하면
      Then 계산이 거부된다

      Examples:
        | 케이스 | 필드    | 값    | 걸리는 규칙        |
        | E-9   | 수량    | 0    | 경계: 수량 < 1     |
        | E-10  | 단가    | -1   | 경계: 단가 < 0     |
        | E-11  | 쿠폰    | -1   | 경계: 쿠폰 < 0     |
        | E-12  | 마일리지 | -1   | 경계: 마일리지 < 0  |

    # §1 검사 순서 정본: "라인이 여러 개면 라인 순서대로 검사해 먼저 나온 라인의 위반이
    # 우선한다" — 뒤집으면 앞 라인이 정상이어도 뒤 라인의 위반은 반드시 걸려야 한다.
    # 첫 라인만 검증하고 통과시키는 얕은 구현을 잡아내는 시나리오.
    Scenario: E-16. 여러 라인 중 뒤쪽 라인만 위반해도 거부된다
      Given 장바구니에 단가 12000원 상품이 2개 담겨 있다
      And 장바구니에 단가 5000원 상품이 1개 담겨 있다
      And 그 두 번째 라인의 수량이 0으로 덮어써진다
      And 쿠폰 0원을 사용한다
      And 마일리지 0원을 사용한다
      When 결제 금액 계산을 요청하면
      Then 계산이 거부된다
```

### 제외한 시나리오 (의도적)

- 쿠폰 0원 · 마일리지 0원만 다른 조합, 라인 수만 늘린 변형 → E-1과 같은 규칙 반복
- 마일리지 1원·상한-1원 같은 인접값 → E-4/E-5 경계로 충분(커버리지용 분기는 단계 4 unit test)
- 예외 타입·메시지 검증 → Gherkin은 "거부된다"까지만 고정, 세부는 단계 4 unit test
- **옛 E-3(Outline의 마일리지 26000 행) 제거** → 입력(라인 2개·쿠폰 5000·마일리지 26000)과
  기대값(1000원)이 E-1과 문자 그대로 동일한 중복이었다. 해당 케이스는 E-1이 전담한다
- **계산 요청 자체가 null**(§1 null 3종 중 ①) → Gherkin은 "장바구니와 쿠폰·마일리지를 주고
  계산을 요청한다"는 문장 구조라 "요청 자체가 없다"를 자연스럽게 표현할 수 없다. 또한 web-app
  경로에서는 REST 진입점의 역직렬화 단계가 먼저 걸러낼 수 있어 계산기 책임인지가 §5에서
  확정된다 → 단계 4 U-1로 위임(§1 검사 순서의 첫 항목이므로 누락이 아니라 위임임을 명시)
- **여러 필드가 동시에 위반할 때의 우선순위**(수량<1 AND 단가<0 등) → §1 검사 순서 정본의
  파생이지만 외부 관찰 결과가 "거부된다"로 동일해 Gherkin으로는 구분되지 않는다. 예외 타입을
  보는 단계 4 U-4로 위임. 단, **라인 순서** 우선순위는 결과가 "통과 vs 거부"로 갈리므로
  Gherkin에 남겼다(E-16)

문구는 한 글자도 바뀌지 않았다** — Protocol Driver 분리가 값을 한 것이다.

- `CartCalculationDriver` — `new CartCalculator()` 직접 호출 → `TestRestTemplate`
  (`POST /carts/{cartId}/checkout`) + `CartRepository`로 MySQL 시드. 공개 메서드
  시그니처는 그대로라 Steps는 driver를 `new` 대신 `@Autowired`로 받는 것만 바뀌었다.
- `Given` "…담겨 있다"는 이제 **MySQL에 라인을 시드**하는 동작이고(`calculate()` 시점에
  `save()` 한 번으로 일괄 시드), `When` "계산을 요청하면"은 **실제 HTTP POST**다.
- 새 파일:
  - `src/test/java/com/example/cart/CucumberSpringConfiguration.java`
    (`@CucumberContextConfiguration` + `@SpringBootTest(webEnvironment = RANDOM_PORT)` +
    `@ActiveProfiles("test")`)
  - `src/test/java/com/example/cart/CartAcceptanceTestConfig.java`
    (Driver를 `@ScenarioScope` bean으로 등록 — 시나리오 간 상태 누출 차단)
  - `src/test/java/com/example/cart/MySqlTestContainer.java` (MySQL 컨테이너 싱글턴 +
    `@DynamicPropertySource`)
  - `src/test/resources/application-test.yml`
- **미결(§6로 위임)**: E-14(라인 목록 null)·E-15(null 라인)는 **REST+DB 채널로 표현할 수
  없다** — 라인이 요청 본문이 아니라 DB에서 오므로 null이 될 수 없다. Driver는 이 두
  경우 명시적 `UnsupportedOperationException`으로 그 사실을 드러낸다(조용한 통과 금지).
  §5 "미결 항목" 참조.

## 5. Walking Skeleton

> **real**(실제 HTTP → 실제 앱 → 실제 MySQL) + **thinnest**(비즈니스 로직 0). Controller는
> 조회 → DTO 변환 → 계산기 위임만 하는 pass-through이고, 계산 규칙(§1)은 여전히 §6 RGB의
> 몫이다 — `CartCalculator.calculate()`는 아직 `UnsupportedOperationException`을 던진다.

### 관통시킨 슬라이스

`POST /carts/{cartId}/checkout` — body `{"coupon":…, "mileage":…}` →
`cartId`로 라인 조회 → `CalculateCartRequest` 조립 → `CartCalculator` 위임 →
`{"finalAmount":…}` (200) / 장바구니 없음 404.

라인은 요청 본문에 없다(§1 채널 결정) — MySQL에서 온다. 인수 조건에 없는 쓰기 API는
만들지 않았다: 시드는 테스트가 Repository로 직접 한다.

### 엔티티 스키마 (최소)

| 테이블 | 컬럼 |
|---|---|
| `carts` | `id` (PK, IDENTITY) |
| `cart_lines` | `id` (PK), `cart_id` (FK NOT NULL), `product`, `unit_price` (BIGINT), `quantity` (INT) |

- 수량·단가에 **DB 제약을 걸지 않았다** — §1의 유효성 검사(수량 < 1, 단가 < 0 거부)는
  계산기의 책임이고, DB가 먼저 막으면 E-9·E-10을 검증할 수 없다.
- 영속 엔티티(`Cart`, `CartLineEntity`)와 도메인 값 객체(`CartLine`)는 **의도적으로 분리**
  했다 — 계산 규칙은 영속성을 알지 못하는 순수 함수로 남는다.

### 영속성 경계 결정 (이후 모든 Controller의 기준 — RGB가 임의로 우회하지 않는다)

| 항목 | 결정 | 근거·강제 수단 |
|---|---|---|
| OSIV | `spring.jpa.open-in-view: false` **명시** | 항목 부재 = 기본값 `true`(켜짐). `application.yml`·`application-test.yml` 양쪽에 명시 |
| 트랜잭션 경계 | **Controller 메서드**(`@Transactional(readOnly = true)`) — 이 단계 한정 | 조회 전용이므로 Hibernate flush가 MANUAL → dirty checking 쓰기가 DB로 새지 않는다 |
| 연관관계 | `Cart.lines`·`CartLineEntity.cart` 모두 **LAZY 유지** | 전역 EAGER 없음. detach로 가드하지 않는다(LAZY와 배타적) |
| 조회 | `CartRepository.findWithLinesById` + `@EntityGraph(attributePaths = "lines")` | 실행 SQL이 `carts left join cart_lines` **한 방**임을 로그로 확인 |
| 저장 | 명시적 `save()`만 | 아래 누출 가드 |
| 응답 | 엔티티가 아니라 **DTO**(`CheckoutResponse`) | Controller 반환 타입으로 강제 |
| 계산기 등록 | `CartConfig`의 `@Bean` | 도메인 클래스에 Spring 애노테이션을 붙이지 않는다 |

### `save()` 누출 가드 (회귀 테스트) — 실패 주입으로 비공허성 확인 완료

`src/test/java/com/example/cart/CartCheckoutWriteLeakGuardTest.java` — 체크아웃 요청 후에도
`cart_lines`가 그대로인지 **aggregate가 아닌 `CartLineJpaRepository`로 DB를 직접 조회**해
확인한다(1차 캐시가 가리지 않도록 테스트에 `@Transactional`을 붙이지 않는다). 계산기는
`@MockBean`으로 대체 — 이 테스트가 보는 것은 계산 결과가 아니라 영속성 경계다.

실패 주입 결과 (경계를 얹는 같은 변경에 가드를 동봉했다):

| 주입 | 결과 |
|---|---|
| Controller에 `cart.getLines().get(0).changeQuantity(99)` 추가 + `readOnly` 제거 | **FAIL** (`expected: 2 but was: 99`, 로그에 `update cart_lines`) |
| 위 변경에서 `readOnly = true`만 복구 | **PASS** (flush 없음) |
| 주입 제거(원상 복구) | **PASS** |

즉 이 가드를 초록으로 유지하는 것은 `readOnly = true` 경계이며, 가드는 그 경계가 사라지면
실제로 빨간불이 된다.

### 관통 확인 (직접 재현)

E-1의 `@pending`을 임시로 떼고 실행 → 실행 SQL 로그가 `insert into carts` →
`insert into cart_lines` ×2 → `select … from carts c1_0 left join cart_lines l1_0 …`
순으로 찍히고, DispatcherServlet이 `CartCheckoutController.checkout` →
`CartCalculator.calculate`까지 도달해 `UnsupportedOperationException`으로 실패했다
(하드코딩·Fake가 아니라 진짜 파이프라인임을 보인 것). 확인 후 `@pending` 원상 복구
(`.feature` 파일은 커밋 기준 byte-identical).

### 미결 항목 (§6 RGB로 위임)

- **U-1(요청 자체 null)·product 필드 null** — §4가 "§5에서 재판단"으로 보류한 항목.
  REST 진입점에서 라인은 DB에서 오므로 `CalculateCartRequest`는 **Controller가 항상 직접
  조립**한다 → 요청 자체 null·라인 목록 null·product null은 REST 경로로 도달 불가하다.
  따라서 이들은 계산기의 공개 API 방어(unit test U-1)로만 남기고, REST 계층에는 별도
  검증을 두지 않는다.
- **E-14·E-15** — 위와 같은 이유로 현재 채널에서 실행 불가. Driver가 명시적 예외로
  드러내며(조용한 통과 금지), 처리 방식(unit test로 이관할지 여부)은 §6에서 결정한다.
- **거부(4xx) 매핑** — §1 유효성 위반 시 어떤 HTTP 상태로 응답할지는 계산기가 던지는
  예외 타입이 정해지는 §6(U-8)에서 확정한다. 지금은 예외 핸들러를 두지 않았다(thinnest).

## 7. JPA Repository

> **아직 미완료.** §5 Walking Skeleton이 이 단계의 **출발점 골격**을 만들어 뒀다 —
> `Cart`·`CartLineEntity`(엔티티), `CartRepository`(`@EntityGraph` 조회),
> `CartLineJpaRepository`(라인 단독 조회). 이 단계에서 남은 일은 그 골격을 도메인 전체를
> 커버하도록 **완성**하고, InMemory 구현과의 **계약 테스트(동등성 검증)**를 세우는 것이다
> (계약 테스트는 부모 클래스에 `@Transactional(propagation = NOT_SUPPORTED)`를 붙여
> 1차 캐시가 DB 접근을 가리는 공허한 검증을 막고 `@AfterEach`로 직접 정리한다).
